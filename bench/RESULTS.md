# 压测：方法与结果

## 问题

「有 AI 味」是主观判断。如果只能靠人眼打分，这个 skill 没法验收，也没法迭代。

所以先把判断标准变成可执行的东西：`scripts/slop-lint.mjs` 的 28 条规则 → 一个 0–100 的分数。然后用**同一个任务、同一个模型**跑两组，看分数动不动。

## 方法

| 项 | 设置 |
|---|---|
| 任务 | 为「拾光」（旅行照片日记 App）做一个单页落地页：hero + 3 个功能卡 + 三档定价 + 一条用户评价 + footer |
| 交付约束 | 单文件 HTML，CSS 内联，无外部资源，中文文案，140–190 行 |
| 提示词 | 除最后一段外逐字相同 |
| 组 A（基线） | 只给任务，不给任何设计方法 |
| 组 B（实验） | 同一段任务，前置一句：读 `SKILL.md` 与它指向的 references，按它的契约、三道闸门和审计流程做；结束时跑 `slop-lint` 并修到 P1 为零 |
| 次数 | 每组 3 次 |
| 评分 | `node scripts/slop-lint.mjs <file> --json` 的 `summary.score` |

**注意**：组 B 的提示词要求它**执行 skill 规定的审计步骤**，而不是只把 SKILL.md 当参考读物。所以测出来的效果是「skill + 它自带的审计闭环」，不是「一段文字的说服力」。这更接近真实用法——skill 的价值本来就在于流程，而不是文风。


| A 基线 | `samples/red-2.html` | 37 | 44 | 33 | 11 |

差值：craft score **+61.3**（38.7 → 100.0），P1 发现 **28.7 → 0**，总发现数 **39.3 → 0**。三份实验组样本在第一次审计时就已零发现，后续只做了检查器覆盖不到的手工打磨（中文断行、320px 导航换行、引号内边距）。

## 基线里到底错了什么

基线样本不是乱码，它们**看起来还行**。问题在于细节债务：

| 典型发现 | 出现次数（red-1） |
|---|---|
| `T001` 字号种数 | 19 种（9.5px 到 110px） |
| `Y001` 中点「·」 | 11 处 |
| `L001` 1px 边框 | 11 处 |
| `R001` 圆角不在 4px 网格 | 5 处（6/7/11/22/30px） |
| `T007` hero 超大字号 | 110px、80px |
| `Y003` 眉标 | 3 处 |

这就是「AI 味」的真实形态：不是难看，是**经不起细看**。远处看是一张完整的落地页，近看每一处都在临时决定。

## 局限（必须读）

1. **单一任务、单一模型、每组 3 次。** 样本量不足以谈统计显著，只能说明「用这个流程做出来的东西，已知的廉价特征显著更少」。
2. **分数只覆盖规则。** 100 分不等于好看、不等于有创意，只等于没有这 28 类已知问题。
3. **规则本身有权重偏见。** P0/P1/P2 的分级与 12/5/2 的权重是本仓库的决定，不是行业标准。改权重会改分数。
4. **0.5px、Radix、黑白灰都是默认值，不是定律。** 它们在多数中文 SaaS / 工具类界面里成立；在儿童、游戏、强品牌场景里需要主动破例，SKILL.md 的「反模式：过度矫正」一节写了怎么破。
5. **静态检查有盲区。** 光影层次、光学对齐、真实内容的排版平衡，检查器看不见，仍然需要人眼。

## 复现

```bash
git clone https://github.com/NPC-NICEPEOPLEC/de-ai-ui.git
cd de-ai-ui
bash bench/score.sh          # 复算本表
node --test tests/*.test.mjs # 检查器自身测试
open examples/before.html examples/after.html
```

样本 HTML 原样提交在 `bench/samples/`，没有手工修饰——你可以自己重新打分，或者用不同的权重改 `scripts/slop-lint.mjs` 的 `WEIGHT` 再看排序。
